## 概要・提供価値

`apps/app` と `apps/admin` のトップ（`/`）は、登録されているユーザーを一覧で表示する。今の一覧は表示だけで、作成・編集・削除は無い。

テンプレートの中では、**データベースから読んだデータを画面に出す一続きの流れの見本**になっている。両アプリに一覧が出ていれば、データベースへの接続と migration・seed が通っていることを画面で確かめられる。

## 背景・解決する課題

- `apps/admin` の一覧は、管理画面の 1 枚目として作った。書き込み系は入れず、データベースを読んで画面に出す流れが管理画面でも同じ形で通ることの確認に絞った（[#234](https://github.com/junkisai/web-app-template/pull/234)）
- データベースを移したときは、両アプリのユーザー一覧が新しいデータベースから表示できることを完了の条件にした（[#257](https://github.com/junkisai/web-app-template/pull/257)）
- `apps/app` の `/` に一覧を置いた理由は記録が無い

一覧が、テンプレートから作られるアプリの利用者のどんな困りごとを解くかを書いた資料は無い。

## 対象ユーザー・スコープ

### 対象ユーザー

| 利用者 | 立場 |
| --- | --- |
| テンプレートを使う開発者 | 一覧を見て、データベースにユーザーが入っていること、それが画面まで届いていることを確かめる |
| `apps/admin` を使う運営者 | 登録済みのユーザーを一覧で見る。管理画面の利用者は社内に限られる想定（[#234](https://github.com/junkisai/web-app-template/pull/234)） |
| `apps/app` の利用者 | `/` で一覧を見る。誰に見せるための一覧かは決まっていない（未確認事項） |

ロールによる違いは無い。

### 対象のアプリ・画面・URL

| アプリ | URL | 画面 |
| --- | --- | --- |
| `apps/app` | `/` | トップ。一覧はページの一部 |
| `apps/admin` | `/` | ユーザー一覧 |

### できる操作

- 登録済みのユーザーを一覧で見る

### 対象外

なし。作成・編集・削除が無いのは後回しにしているだけで、やらないと決めたものではない（実装から読み取れる現状）。

## ゴール・成功条件

- データベースに入っているユーザーが、両アプリの画面で確かめられる
- テンプレートの見本として、データベースを読んで画面に出す流れが両アプリで同じ形で動いている（作りは [architecture/directory-structure.md](../architecture/directory-structure.md)）

測定指標は定めていない。

## 振る舞い

- **両アプリの `/` は、登録されているユーザーを一覧で出す**
- **デプロイした環境では、両アプリの一覧に同じユーザーが出る。** 両アプリが 1 つのデータベースを共有している（[architecture/overview.md のデータベース](../architecture/overview.md#データベース)）
- **ローカルの開発環境では、アプリごとにデータが分かれる。** そのため、両アプリで出るユーザーが食い違うことがある。これはデータベースを移したときに許容すると決めた（[#257](https://github.com/junkisai/web-app-template/pull/257)）
- **`apps/admin` の一覧は表で出す。** 管理画面の 1 枚目として置いた画面

## 業務ルール・制約

### ユーザーの持つ情報

1 人のユーザーは次の情報を持つ。テーブル・列の名前と型の正本は [`packages/db/src/schema.ts`](../../packages/db/src/schema.ts)。

| 項目 | 必須 |
| --- | --- |
| ID | 必須。ユーザーごとに一意 |
| 名前 | 必須 |
| 登録日時 | 必須 |
| 更新日時 | 必須 |

### 権限・公開範囲

- `apps/admin` の一覧は、管理画面の公開範囲の要件に従う（[管理画面の PRD](admin-console.md)）
- `apps/app` の一覧を誰に見せてよいかは決まっていない（未確認事項）

## 状態遷移

なし。一覧は読み取りだけで、ユーザーの状態を持たない。

## 例外・境界条件

「現状」と付けた行は、今そう動いているという記録で、要件として決まったものではない（[扱い](README.md#実装から読み取れる現状の扱い)）。

| 条件 | 結果 |
| --- | --- |
| ユーザーが 0 件 | 現状は、`apps/admin` が「ユーザーがいません」と、seed を流すかアプリ側から作るよう促す案内を出す。`apps/app` は案内を出さない |
| ユーザーが多い | 現状は、全件を出す。件数の上限とページングは無い |
| 日時として読めない値が入っている | 現状は、`apps/admin` がその値をそのまま出す |
| 読み込みに失敗する | 現状は、サーバーのログに例外を出して、そのまま投げる。画面に専用のエラー表示は無い。何を見せるべきかは決まっていない |
| ローカルで、アプリごとにデータが違う | 両アプリの一覧が食い違う。許容されている（振る舞い） |
| `/login` でアカウントを作る | 一覧には出ない（未確認事項） |

## 受け入れ条件

- データベースに入っているユーザーが、`apps/app` の `/` と `apps/admin` の `/` の両方に出る
- デプロイした環境では、`apps/app` の `/` と `apps/admin` の `/` に同じユーザーが出る

## 実装から読み取れる現状・未確認事項

### 実装から読み取れる現状

**ここに書いたものは要件ではなく、今そう動いているという記録。** 変更を禁じる制約でもない。変更を頼まれたら、その要求を新しい判断の起点にする（[扱い](README.md#実装から読み取れる現状の扱い)）。「例外・境界条件」の表で「現状」と付けた行も同じ扱い。

- **作成・編集・削除の画面は無い。** 一覧は読み取りだけ。「この先もやらない」と決めたものではなく、管理画面を作ったときに後回しにしたもの（[#234](https://github.com/junkisai/web-app-template/pull/234)）
- **`apps/app` の `/`** は名前だけを縦に並べる。ログインしていなくても、登録されている全員の名前が見える
- **`apps/admin` の `/`** は見出し「ユーザー」と「登録済みのユーザーが N 件あります。」を出し、表の列は ID・名前・登録日時・更新日時。日時は日本語の表記・日本時間で出す
- **並び順の指定は無い。** 全件を取り、並べ替えを指定していない（`features/users/api/get-users.ts`）

### 未確認事項

- **ログインで作ったアカウントは一覧に出ない。** 一覧が読むのは業務側のユーザーで、`/login` でアカウントを作ると書き込まれるのは認証側のユーザー。2 つは別のテーブルになっている（[architecture/overview.md の schema](../architecture/overview.md#schema)）。2 つを別のものとして扱うのか、いずれ結び付けるのかは決まっていない。`apps/admin` の 0 件の案内は「アプリ側からユーザーを作成してください」と言っているが、今の実装では作っても一覧には出ない
- **日時の形式が決まっていない。** 表示側のコメントは ISO 8601 を前提にしているが、seed の `created_at` は `2026-03-25T17:49:50.847Z`、`updated_at` は `2026-03-25 18:57:39` と形式が違う
- **並び順・件数の上限・ページングの要件**が決まっていない
- **読み込みに失敗したときに何を見せるか**が決まっていない
- **`apps/app` の一覧を誰に見せてよいか。** 今は未ログインの人にも全員の名前が出る。テンプレートの見本として出しているだけなのか、一般の利用者に見せる前提なのかは決まっていない
- **テンプレートとしての位置づけ。** 一覧を、テンプレートから作るアプリでも育てる基礎機能とするか、作り替える前提の見本とするか（[product.md の未確認事項](../product.md#未確認事項仮説)）
