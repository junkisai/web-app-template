# prds

**機能ごとに、なぜ要るのか（目的・課題・ゴール）と、何を満たすべきか（要件・振る舞い・受け入れ条件）を書く場所。** 1 つの機能に 1 ファイルの Living Document で、要件や振る舞いが変わるたびに同じファイルを書き換える。

過去の要件と判断の経緯は、その変更を入れたコミットと PR から辿る。PRD には今有効なものだけを置く。

## 他の文書との違い

| | 答える問い | 時点 | 実装後 |
| --- | --- | --- | --- |
| [product.md](../product.md) | プロダクト全体は何のためにあるか | 常に今 | 目的・価値・成功条件が変わったら更新する |
| **prds/** | **この機能はなぜ要り、何を満たすべきか** | **常に今** | **実装に合わせて更新する** |
| [architecture/](../architecture/overview.md) | 今どう組まれているか | 常に今 | 構成・規約が変わったら更新する |

- **product.md と PRD。** product.md はプロダクト全体の Why、PRD は機能ごとの Why と What。機能の目的が product.md の方向性と食い違ったら、どちらかを決めつけずに報告する
- **PRD と PR・コミット。** **今の要件は PRD、そこに至った過程は PR の本文とコミット**に分ける。PRD から経緯を知りたいときは、「関連資料」の PR か、`git log` で PRD を変えたコミットから辿る
- **PRD と architecture。** PRD は利用者や外部から見た要件、architecture はそれを今どう実現しているか。同じ機能でも、「認証を無効にできる」は PRD、「`ENABLE_AUTH` で切り替え、`auth` を `404` を返す handler に差し替える」は architecture に書く

## 書くこと・書かないこと

書く。

- **その機能が要る理由。** 誰の、どんな状況を良くするためのものか。根拠（README、PR、画面の案内文、要求の記録）のあるものだけ
- 誰が・どの画面や URL で・何をできるか
- 条件ごとの期待する結果。状態や権限による振る舞いの違い、他の機能との連動
- 守るべき要件（入力の条件、権限、公開範囲、データの扱い、プライバシーとセキュリティ）
- 受け入れ条件。満たしたかどうかを判定できる書き方で
- **外から観測できる API の契約。** 応答のステータスやエラーコードなど、クライアントが頼りにするもの。API 契約の専用の文書があるならそれを正本にしてリンクし、無いなら PRD に書く

書かない。

- **実装方法と技術選定。** どのライブラリ・基盤で実現しているか、環境変数の名前、binding、テーブル・列の名前と型、コードの置き場所は [architecture/](../architecture/overview.md) とコードが正本。PRD からはリンクするだけにする。ただし**セキュリティやデータ保護の要求は、技術的な話題でも PRD に書いてよい**（例: パスワードを平文で保存しない）。書くのは「何を守るか」で、「どう守るか」は architecture に書く
- **技術選定の経緯。** なぜそれを選んだかは、その変更の PR の本文とコミットに書く
- **手順。** セットアップ・デプロイ・migration・secrets の入れ方は、ルートの [README.md](../../README.md) と [runbooks/](../runbooks/) に書く
- **未実装の変更案。** 実装が入るまで PRD は書き換えない
- **確かめられなかった目的・課題・KPI。** 下の「根拠が確かめられないとき」に従う

## 根拠が確かめられないとき

**コードにあるからといって、それが意図された仕様だとは限らない。** 根拠のない補完はしない。

- 根拠があるもの（README、PR の説明、要求の記録、意図を書いたコードコメント）だけを「振る舞い」「業務ルール・制約」「受け入れ条件」に書く。根拠は本文か「関連資料」に残す
- **目的・課題・ゴールを想像で書かない。** 記録が無ければ「記録が無い」と書き、確かめたいことは「未確認事項」に置く。数値の指標が決まっていないのに KPI を置かない
- **過去の PR とコミットは、当時の意図や判断を確かめるための資料として読む。** 今有効な要件として採るときは、後から入った変更、今の実装、最新の要求と照合する。過去に承認されたという事実だけで、今の要件だと決めない。食い違っていたら「未確認事項」に書く
- コードからは読み取れるが要件として決まっていないもの（意図が確かめられない振る舞い、後回しにしていて今は無いもの）は「実装から読み取れる現状」に分けて書く。扱いは次の節にある
- 決まっていないこと、食い違いが見つかったことは「未確認事項」に書く。決まったら本文へ移し、ここから消す

### 「実装から読み取れる現状」の扱い

この節は、今そう動いているという観測の記録で、**要件でも、変更を禁じる制約でもない。**

- ユーザーから明示的に変更を頼まれたら、その要求を新しい判断の起点にする。「意図が確かめられていない」「今そうなっている」は、変更を断る理由にならない
- ただし、安全性やデータへの影響があるとき、設計上の未決事項に関わるときは、必要な確認・承認を取ってから進める
- 変えたら、この節も書き換える。変更の中で要件として決まったことは「振る舞い」「業務ルール・制約」「受け入れ条件」へ移す

**今は無いもの・今の実装の限界も、ここに書く。** 「認証が無い」「読み取りしかできない」のような状態を「振る舞い」や「受け入れ条件」に書くと、守り続けるべき要件に見え、機能を足すこと自体が要件違反に見えてしまう。今は無いことを「対象ユーザー・スコープ」の対象外に書くのも同じ理由で避ける。対象外に書くのは、やらないと決めた記録があるものだけ。

「例外・境界条件」の表で「現状」と付けた行も、この節と同じ扱いになる。

## 要件を変えるとき

要件や振る舞いの変更の要求は、**新しい検討の起点**として扱う。過去の PR やコミットに違うことが書いてあっても、今の PRD に「実装から読み取れる現状」として書いてあっても、それは変更を断る理由にならない。

1. 今の PRD と [architecture/](../architecture/overview.md) を読み、要求との差分と影響範囲を洗い出す。プロダクト全体の目的や価値に関わるなら [product.md](../product.md) も読む
2. 既存の制約（安全性、技術的な制約、他の機能との依存）と衝突するなら、影響・リスク・変更案を示して判断を仰ぐ。制約を黙って無視しない
3. 採った案・採らなかった案とその理由は、実装の PR の本文に書く（[AGENTS.md の「判断の理由を残す」](../../AGENTS.md#判断の理由を残す)）
4. **実装が入った PR で PRD を書き換える。** 実装より先に書き換えない。実装したのに PRD を直さないままにもしない。技術構成が変わったら architecture を、手順が変わったら runbooks を、プロダクト全体の目的・価値・成功条件が変わったら product.md を、同じ PR で書き換える

## ファイル名

機能を表す英小文字の kebab-case にする。日付は付けない。

```text
<機能>.md
```

例: `auth.md`、`users.md`

- **1 つの機能に PRD は 1 ファイル。** 要件が変わったら、新しいファイルを足さずに同じファイルを書き換える。同じ機能の PRD が 2 つあると、どちらが今の要件かわからなくなる
- **名前は変えない。** 改名すると、他の文書や過去の PR からのリンクが切れる

機能の名前は企画やデザインの会話に出てくる言葉で付ける（[architecture/directory-structure.md](../architecture/directory-structure.md) の「まとまり」の付け方と同じ）。

## 書き方

[`_template.md`](_template.md) をコピーして使う。frontmatter の `title`・`scope` は残す。

| 節 | 何のためにあるか |
| --- | --- |
| 概要・提供価値 | この機能が何をし、誰にどんな価値を渡すか |
| 背景・解決する課題 | なぜこの機能が要るのか。根拠が無ければ「記録が無い」と書く |
| 対象ユーザー・スコープ | 誰の、どのアプリ・URL・画面の話か。できる操作。やらないと決めた範囲 |
| ゴール・成功条件 | 何が実現されれば成功か。測定指標は、決まっているときだけ書く |
| 振る舞い | 条件ごとの期待する結果。根拠のある、今有効なもの |
| 業務ルール・制約 | 入力、判定、データの扱い、権限・公開範囲、プライバシーとセキュリティの要件。実現方法ではなく、満たすべきこと |
| 状態遷移 | 状態を持つ機能の、状態・遷移の条件・できる操作 |
| 例外・境界条件 | 0 件、権限が無い、不正な入力、通信の失敗、重複操作、データの欠損など |
| 受け入れ条件 | 満たしているかを判定できる形で。チェックボックスにせず、ふつうの箇条書きにする（未チェックが残作業に見えるため。テストを流した結果は PR に書く） |
| 実装から読み取れる現状・未確認事項 | 今そう動いているだけの振る舞いと今は無いもの、決まっていないことと食い違っていること |
| 関連資料 | product、architecture、経緯をたどる PR、runbook、API 契約、関連する PRD、根拠になる実装とテスト |

**ゴールと受け入れ条件は分ける。** ゴールは「何を達成したいか」、受け入れ条件は「どう動けば正しいか」。

該当しない節は「なし」と書いて残す。
