## 概要・提供価値

`apps/app` の利用者は、メールアドレスとパスワードでアカウントを作り、ログインとログアウトができる。OAuth のログインは、資格情報を設定した provider だけが使える。認証は環境ごとに丸ごと無効にできる。

テンプレートを使う開発者にとっては、**アカウント作成からセッションの確認までが最初から動く状態**で手に入り、自分のアプリの認証をそこから作り始められる。

## 背景・解決する課題

- 認証は「Better Auth ベースの認証テンプレート」として足した。目的は、サインアップ・サインイン・サインアウト・セッションの確認までを、手元で動作確認できる状態にすること（[#150](https://github.com/junkisai/web-app-template/pull/150) の説明）
- `/login` は、その流れを端から端まで確かめるための画面として置いている。`/login` の案内文は "This screen exists to validate the flow end to end, not to hide it behind a placeholder."、`/` の案内文は "Use the login screen to create an account and confirm the session state."
- OAuth は、provider ごとの資格情報を入れるだけで有効になるようにしている（ルートの [README.md の「OAuth provider を有効にする」](../../README.md#oauth-provider-を有効にする)）
- 認証を丸ごと止める切り替えがある（#150 の「runtime toggle」）。**何のための切り替えか（認証を使わないアプリのためか、一時的に止めるためか）は記録が無い**（未確認事項）

テンプレートから作られるアプリの利用者が、認証について何に困っているかを書いた資料は無い。

## 対象ユーザー・スコープ

### 対象ユーザー

| 利用者 | 立場 |
| --- | --- |
| `apps/app` の利用者 | アカウントを作り、ログイン・ログアウトする。ロールの区別は無い |
| テンプレートを使う開発者 | 認証を有効にするか、どの OAuth provider を使うかを環境ごとに決める。`/login` で認証の流れを確かめる |

### 対象のアプリ・画面・URL

| アプリ | URL | 画面 |
| --- | --- | --- |
| `apps/app` | `/api/auth/*` | なし（認証 API） |
| `apps/app` | `/login` | ログイン画面 |
| `apps/app` | `/` | トップ（セッションの状態を表示する） |

### できる操作

- メールアドレスとパスワードでアカウントを作る
- メールアドレスとパスワードでログインする
- 資格情報を設定した provider で OAuth のログインをする
- ログアウトする
- ログイン中かどうか、誰としてログインしているかを確かめる

### 対象外

なし。管理画面（`apps/admin`）の認証・認可は、この PRD ではなく[管理画面の PRD](admin-console.md) で扱う。

## ゴール・成功条件

- テンプレートを使う開発者が、セットアップの直後に `/login` でアカウント作成・ログイン・ログアウトを行い、`/` でセッションの状態を確かめられる（#150）
- OAuth の provider を、資格情報を設定するだけで使い始められる（README）
- 認証を無効にした環境では、認証の入口が閉じている

測定指標は定めていない。

## 振る舞い

### 認証の有効・無効

認証は環境ごとに有効・無効を切り替えられる。**既定は有効。** 切り替えの設定と受け付ける値は [architecture/overview.md の環境変数](../architecture/overview.md#環境変数)にある。

| 認証 | `/api/auth/*` |
| --- | --- |
| 有効（既定） | 認証 API として応答する |
| 無効 | 認証の処理をせず `404` を返す。本文は JSON で、`code` が `AUTH_DISABLED` |

無効のときの `404` / `AUTH_DISABLED` は、クライアントから見える API の契約として扱う。API 契約の専用の文書は無いので、この表を正本にする。

### メールアドレスとパスワード

- メールアドレスとパスワードでアカウントを作れる
- 作ったアカウントの資格情報でログインできる
- ログイン中はログアウトできる（#150）

### OAuth

次の provider に対応する。**provider ごとの資格情報（クライアント ID とクライアントシークレット）が両方そろったときだけ、その provider が有効になる。** 片方だけなら有効にならない。資格情報を渡す環境変数の名前は [architecture/overview.md の認証](../architecture/overview.md#認証)にある。

Apple、Discord、Facebook、GitHub、GitLab、Google、LinkedIn、Microsoft、Slack、Spotify、Twitch、X

### セッションの確認

`/` は、ログイン中かどうかを表示する。未ログインなら `/login` へ案内する（`/` の案内文）。

### 他の機能との連動

- 認証で作ったアカウントは、[ユーザー一覧](users.md)の元データとは別になっている。結び付けるかは決まっていない（未確認事項）
- 管理画面（`apps/admin`）は、この認証を使っていない（[管理画面の PRD](admin-console.md)）

## 業務ルール・制約

- **認証を無効にした環境では、認証 API は認証の処理をせず、`404` / `AUTH_DISABLED` に固定する**
- **OAuth の provider は、資格情報がそろっていないかぎり有効にしない**
- **パスワードは平文で保存しない。** 照合用のハッシュだけを持つ。#150 でハッシュの処理を自前で実装している（方式は [architecture/overview.md の認証](../architecture/overview.md#認証)）

パスワードの長さ・文字種、メールアドレスの確認の要否は、要件として決まっていない（未確認事項）。

## 状態遷移

### セッション

| 状態 | できる操作 | 遷移 |
| --- | --- | --- |
| 未ログイン | アカウント作成、ログイン | ログインに成功 → ログイン中 |
| ログイン中 | セッションの確認、ログアウト | ログアウト → 未ログイン |

アカウント作成に成功すると、そのままログイン中になる。これは今の実装の振る舞いで、要件として決めたものではない（実装から読み取れる現状）。

### 認証の有効・無効

環境ごとの設定で決まる。セッションの状態とは別で、無効の環境ではどちらの遷移も起きない。

## 例外・境界条件

「現状」と付けた行は、今そう動いているという記録で、要件として決まったものではない（[扱い](README.md#実装から読み取れる現状の扱い)）。

| 条件 | 結果 |
| --- | --- |
| 認証が無効な環境で、`/api/auth/*` に `GET` / `POST` する | `404` と `code: "AUTH_DISABLED"` を返す |
| 認証が無効な環境で、`/login` や `/` を開く | 決まっていない。現状は画面がそのまま出て、操作すると裏の API が `404` を返す |
| provider の資格情報が片方しかない | その provider は有効にならない |
| 認証の切り替えの設定に、受け付けない値を入れる | 環境変数の検証でエラーになる（[architecture/overview.md の環境変数](../architecture/overview.md#環境変数)） |
| ログイン・アカウント作成に失敗する（資格情報の誤りなど） | 現状は、返ってきたエラーの文言を画面に出す。何を見せるべきかは決まっていない |
| パスワードが短すぎる・長すぎる | 現状は受け付けない。画面は 8 文字未満を送信前に止め、サーバーは 8〜128 文字の外を拒む。どちらもアプリで決めた値ではない（[architecture/overview.md の認証](../architecture/overview.md#認証)） |
| 登録済みのメールアドレスで、もう一度アカウントを作る | 現状は、別のメールアドレスを使うよう求めるエラー（`422`、`USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`）になる。要件としては決まっていない |
| 認証 API が失敗の応答を返す、または処理が例外で落ちる | 現状は、サーバーのログに記録する（記録する内容は [architecture/overview.md の認証](../architecture/overview.md#認証)） |

## 受け入れ条件

- 認証が有効（既定）の環境で、`/api/auth/*` が認証 API として応答する
- 認証が無効の環境で、`GET` / `POST` の `/api/auth/*` が `404` と `code: "AUTH_DISABLED"` を返す
- `/login` でメールアドレスとパスワードのアカウントを作り、同じ資格情報でログインできる
- ログイン中にログアウトすると、未ログインに戻る
- provider のクライアント ID とクライアントシークレットがそろったときだけ、その provider が有効になる

## 実装から読み取れる現状・未確認事項

### 実装から読み取れる現状

**ここに書いたものは要件ではなく、今そう動いているという記録。** 変更を禁じる制約でもない。変更を頼まれたら、その要求を新しい判断の起点にする（[扱い](README.md#実装から読み取れる現状の扱い)）。「例外・境界条件」の表で「現状」と付けた行も同じ扱い。

- **`/login` の画面。** 未ログインのときは「Sign in」と「Create account」を切り替えて使う。Create account は表示名・メールアドレス・パスワードを、Sign in はメールアドレス・パスワードと「Keep the session alive on this browser」（既定でオン）を受け取る。成功するとセッションを取り直して `/` へ移る
- **アカウント作成の直後は、ログイン中になる**
- **`/login` に OAuth の入口は無い。** provider を有効にしても、画面からはメールアドレスとパスワードでしかログインできない。OAuth は認証 API としてだけ有効になる
- **メールアドレスの確認は無い。** 確認メールを送らず、作ったアカウントはすぐ使える
- **ログイン中の表示。** `/login` と `/` は、ログイン中なら名前・メールアドレス・ユーザー ID と「Sign out」を出す。未ログインなら、`/` はログイン画面へのリンクと案内を出す
- **画面の文言は英語。** `apps/admin` の画面は日本語

### 未確認事項

- **認証が無効な環境で、`/login` と `/` がどう振る舞うべきか。** 今は画面がそのまま出て、裏の API が `404` を返す
- **パスワードの要件（長さ・文字種）を要件として決めるか。** 移行前の spec は「見えているのは画面側の 8 文字以上だけ」としていたが、2026-11-15 に確かめたところ、サーバー側でも認証ライブラリの既定で 8〜128 文字に制限されていた。どちらもアプリで決めた値ではない
- **登録済みのメールアドレスで作ろうとしたとき、何を返すべきか。** 今のエラーは、そのメールアドレスが登録済みだと相手に伝わる
- **ログイン・アカウント作成に失敗したとき、何を見せるべきか**
- **メールアドレスの確認を要件にするか**
- **OAuth の入口を画面に置くか**
- **認証を丸ごと無効にする切り替えが、何のためにあるか**
- **ログインで作ったアカウントが、ユーザー一覧に出ない。** 一覧の元データと認証のアカウントが別になっている（[ユーザー一覧の未確認事項](users.md#未確認事項)）
- **`apps/admin` に認証をいつ・どの方式で入れるか。** 「外部に公開して運用する前に必ず要る」ことだけが決まっている（[管理画面の PRD](admin-console.md)）
- **テンプレートとしての位置づけ。** `/login` は動作確認のための画面として置かれている。テンプレートから作るアプリでもこの画面を育てるのか、置き換える前提の見本なのかは決まっていない（[product.md の未確認事項](../product.md#未確認事項仮説)）
