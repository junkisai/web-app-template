# design-docs

**作る前に「何を・なぜ・どう作るか」を 1 枚にまとめる場所。** コードを書く前に書き、レビューで合意してから実装に入る。

## なぜ spec ではなく design doc なのか

spec は決まったことの一覧で、**決める過程が残らない。** 後から読んだ人（次の自分、他のメンバー、AI エージェント）は「なぜこの形なのか」を再現できず、同じ議論をもう一度やる。

design doc は過程ごと残す。**やらないことと、検討して捨てた案が本文に入る。** これがあると、

- 実装中にスコープが広がりかけたとき、「やらないこと」に書いてあるかで止められる
- 「やっぱりこっちの作りでは」と思ったとき、すでに捨てた案かどうかが「検討した他の案」でわかる
- AI エージェントに実装させるとき、判断の前提ごと渡せる。仕様だけ渡すと、書いていない部分を勝手に埋められる

書くのは実装者。**合意を取るための文書であって、報告書ではない。** 完成した機能の説明を後から書くのは design doc ではない。

## いつ書くか

| | design doc |
| --- | --- |
| 画面を足す・URL を増やす | 書く |
| データの持ち方を変える（スキーマ変更） | 書く |
| 既存の画面の振る舞いを変える | 書く |
| ライブラリ・基盤の選定 | 書く |
| 文言修正・スタイル調整・リファクタリング | 書かない |
| バグ修正 | 書かない（原因と直し方は PR に書く） |

**迷ったら書く。** 書き始めて 10 分で書くことがないなら、それは書かなくていい変更だった、という判断でよい。

## ファイル名

リポジトリ共通の規約に従い、書き始めた日を prefix にする。

```text
<YYYYMMDD>_<topic>.md
```

例: `20260826_user-invitation.md`

## 書き方

[`_template.md`](_template.md) をコピーして使う。各節は次の役割で置いてある。

| 節 | 何のためにあるか |
| --- | --- |
| 概要 | ここだけ読んで他の人に説明できる状態にする |
| 背景 | なぜ今これが要るのか。書けないものは、まだ作るときではない |
| ゴール | 達成したかを判定できる形にする |
| やらないこと | 実装中のスコープの広がりを止める |
| 設計 | 画面・URL・置き場所・データ・処理の流れ |
| 検討した他の案 | 捨てた案を残す。後から一番効く |
| 影響範囲 | 壊れうるものを先に挙げる |
| 未決事項 | 決まっていないことを隠さない |

**設計の「置き場所」は [architecture/20260819_directory-structure.md](../architecture/20260819_directory-structure.md) の判断フローで決める。** ここでディレクトリまで決めておくと、実装時に迷わない。

該当しない節は「なし」と書いて中身を消す。**節ごと消さない。** 空でないことより、考えた上で空だとわかることのほうが役に立つ。

## status の進め方

frontmatter の `status` で状態を持つ。

| status | 意味 |
| --- | --- |
| `draft` | 書いている途中。まだ読まなくていい |
| `review` | 読んでほしい。ここで合意を取る |
| `approved` | 合意済み。実装に入ってよい |
| `implemented` | 実装が入った。`pr` に実装 PR を書く |
| `superseded` | 別の design doc が置き換えた。冒頭に後継へのリンクを足す |

**`review` から `approved` に進める条件は「未決事項」が空になること。** 未決のまま実装に入ると、その判断はコードを書く人の手元で勝手に決まる。

## 実装後は追わない

**`implemented` になった design doc は、その時点の判断の記録として凍結する。** 後から実装が変わっても書き換えない。書き換えると「いつ何を決めたか」が消える。

方針が変わったら、新しい design doc を書いて古いほうを `superseded` にする。

**恒常的な規約になったもの（構成の規約、依存の向き、命名）は [architecture/](../architecture/) へ移す。** design doc は「あのとき何を決めたか」、architecture は「今どうなっているか」。常に最新なのは architecture のほうだけ。
