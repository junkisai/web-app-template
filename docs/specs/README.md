# specs

**今このシステムが何を満たすべきか**を書く場所。機能・ドメインごとに 1 ファイルにまとめ、仕様が変わるたびに書き換える Living Document として扱う。

## design doc との違い

| | specs | design-docs |
| --- | --- | --- |
| 書くこと | 現在有効な要件・振る舞い・制約・受け入れ条件 | 変える理由、実現方法、検討した他の案、トレードオフ |
| 時点 | 常に今 | 書いた日の時点 |
| 実装後 | 実装に合わせて更新する | 原則凍結する |
| ファイル名 | `<機能>.md`（日付なし） | `YYYYMMDD_<topic>.md`（書き始めた日） |

spec だけでは「なぜこの形なのか」が残らない。design doc だけでは、どれが今も有効な決定なのかがわからない。だから両方を持ち、**今の姿は spec、そこに至った過程は design doc** と分ける。spec から経緯を知りたいときは、frontmatter の `design_docs` から辿る。

## 書くこと・書かないこと

書く。

- 誰が・どの画面や URL で・何をできるか
- 入力と出力、状態による振る舞いの違い
- 守るべき制約（権限、公開範囲、データの扱い）
- 受け入れ条件。満たしたかどうかを判定できる書き方で

書かない。

- **実装方法と技術選定の経緯。** どのライブラリで実現しているか、なぜそれを選んだかは design doc と [architecture/](../architecture/) に書く。spec からはリンクするだけにする
- **未実装の変更案。** これからやることは design doc に書く。実装が入るまで spec は書き換えない
- **確かめられなかった仕様。** 下の「仕様が確かめられないとき」に従う

## 仕様が確かめられないとき

**コードにあるからといって、それが意図された仕様だとは限らない。** 根拠のない補完はしない。

- 根拠があるもの（合意済みの design doc、README、要求の記録、意図を書いたコードコメント）だけを「振る舞い」「制約」「受け入れ条件」に書く。根拠は本文か「関連」に残す
- コードからは読み取れるが、意図が確かめられないものは「実装から読み取れる現状」に分けて書く。**ここに書いたものは仕様ではない。** 変えてよいかどうかは、変える前に確認する
- 決まっていないこと、食い違いが見つかったことは「未確認事項」に書く。決まったら本文へ移し、ここから消す

## 仕様を変えるとき

仕様変更の要求は、**新しい検討の起点**として扱う。過去の design doc に違うことが書いてあっても、それは変更を断る理由にならない。

1. 今の spec と [architecture/](../architecture/) を読み、要求との差分と影響範囲を洗い出す
2. 既存の制約（安全性、技術的な制約、他の機能との依存）と衝突するなら、影響・リスク・変更案を示して判断を仰ぐ。制約を黙って無視しない
3. 重要な変更なら design doc を書き、ユーザーの承認を得てから実装する（[design-docs/README.md](../design-docs/README.md)）
4. **実装が入った PR で spec を書き換える。** 実装より先に書き換えない。実装したのに spec を直さないままにもしない

## ファイル名

機能・ドメインを表す英小文字の kebab-case にする。日付は付けない。

```text
<機能>.md
```

例: `auth.md`、`users.md`

- **1 つの機能に spec は 1 ファイル。** 仕様が変わったら、新しいファイルを足さずに同じファイルを書き換える。同じ機能の spec が 2 つあると、どちらが今の仕様かわからなくなる
- **名前は変えない。** 改名すると、凍結した design doc や他の文書からのリンクが切れる

機能の名前は企画やデザインの会話に出てくる言葉で付ける（[architecture/directory-structure.md](../architecture/directory-structure.md) の「まとまり」の付け方と同じ）。

## 書き方

[`_template.md`](_template.md) をコピーして使う。

| 節 | 何のためにあるか |
| --- | --- |
| 概要 | この機能が何かを 3 行以内で |
| 対象 | どのアプリ・URL・画面の話か。対象外も書く |
| 振る舞い | 根拠のある、今有効な振る舞い |
| 制約 | 守るべき条件。破ると問題になるもの |
| 受け入れ条件 | 満たしているかを判定できる形で |
| 実装から読み取れる現状 | 意図が確かめられていない、コード上の振る舞い。仕様ではない |
| 未確認事項 | 決まっていないこと、食い違っていること |
| 関連 | 経緯の design doc、構成の architecture、手順の runbook |

該当しない節は「なし」と書いて残す。
